# Backlog Vinyl Collection AI

Текущий этап 1 — полный локальный MVP с обычным веб-интерфейсом без AI и реальными Google Sheets. Этап 2 — публикация на собственном VPS и публичный гостевой read-only просмотр коллекции; этап 3 — AI-чат, фото, интернет-уточнения и естественный язык как дополнительный интерфейс. [README](../README.md) определяет границы; действующие спецификации определяют поведение. Номера стабильны и не задают порядок реализации. Исторические причины ниже описывают прежний прототип, а не текущие ограничения этапов. Статусы «согласовано», «требует спецификации», «реализовано», «проверено» различаются. Ни один пункт не считается реализованным только из-за включения в этап.

## 1. Дополнительный жанр

- **Этап:** 1. **Статус:** согласовано. **Требования:** [документ](data-rules.md).

- **Описание:** Принятое продуктовое решение: добавить необязательное поле `Дополнительный жанр`. Если оно заполнено, значение должно отличаться от поля `Жанр`. Поле позволяет не хранить несколько жанров списком в одной ячейке. При поиске по жанру на этапе 1 проверять оба поля: запись подходит, если жанр найден в `Жанр` или `Дополнительный жанр`.
- **Причина первоначального откладывания (история):** Первый прототип только отображал согласованные на тот момент поля. Теперь дополнительный жанр включён в модель этапа 1 и общие правила данных; это не означает завершения его реализации.

## 2. Редактирование существующей записи

- **Этап:** 1. **Статус:** требует спецификации. **Требования:** [документ](edit-record-spec.md).

- **Описание:** Редактирование записей основной коллекции и wish-list остаётся в MVP. Отдельные спецификации будут подготовлены перед реализацией этих операций.
- **Причина первоначального откладывания (история):** Сознательно отложено действующей документацией; первый прототип работает только на чтение. Это не дефект.

## 3. Удаление существующей записи

- **Этап:** 1. **Статус:** реализовано для основной коллекции; контролируемый реальный acceptance пройден. Wish-list реализован и проверен автоматически; реальный acceptance предстоит. **Требования:** [документ](delete-record-spec.md).
- **Описание:** Удаление выбранной записи основной коллекции или wish-list: выбор записи → подтверждение удаления → удаление → проверка результата → сообщение об успехе только после успешной проверки.
- **Причина первоначального откладывания (история):** Первый прототип не изменяет данные. Удаление остаётся в MVP; подробности интеграции определяются перед реализацией.
- **Граница:** Undo не входит в текущий MVP и вынесен в пункт 21.

## 4. Перенос купленной пластинки из wish-list в основную коллекцию

- **Этап:** 1. **Статус:** реализовано; автоматические тесты пройдены, реальный acceptance предстоит. **Требования:** [документ](../README.md).

- **Описание:** Реализован перенос с подтверждённым созданием коллекции до удаления wish-list, отдельным частичным успехом и явным завершением удаления по выбранному дублю. [Контракт](add-wishlist-record-spec.md#перенос-wish-list--collection). Журнал, idempotency infrastructure и rollback не вводятся; междокументная неатомарность принята как ограничение MVP. Строгая атомарность отложена до подходящего хранилища.
- **Причина первоначального откладывания (история):** Ранее самостоятельный сценарий переноса не был определён; решение владельца зафиксировано 2026-09-22.

## 8. Технический идентификатор записи

- **Этап:** 1. **Статус:** правила обеих моделей согласованы; генерация и проверка UUID обеих коллекций реализованы. Миграция не реализована. **Требования:** [документ](data-rules.md).

- **Описание:** Для основной коллекции и wish-list согласован постоянный UUID в отдельной колонке `ID` Sheets, генерируемый приложением. Для существующих записей без ID предусмотрена отдельная одноразовая миграция. GET не исправляет ID; после миграции отсутствующий, некорректный или повторяющийся ID вызывает явную ошибку. Правила описаны в модели данных. Требование миграции относится к обоим документам и само по себе не разрешает изменять реальные таблицы.
- **Причина первоначального откладывания (история):** Для первого локального просмотра идентификатор не требовался. Теперь формат и хранение ID обеих моделей согласованы; реализация и проверка ещё не выполнены.

## 9. Реальное подключение двух Google Sheets-документов

- **Этап:** 1. **Статус:** подключено, реальное чтение проверено; acceptance записи wish-list предстоит. **Требования:** [документ](../README.md).

- **Описание:** Подключены основная коллекция и wish-list, хранящиеся в двух отдельных Google Sheets-документах, через собственный API и слой доступа к данным по архитектуре README. Прямой доступ браузера к Sheets API исключён; UI использует внутреннюю модель. Контракты GET/POST/DELETE основной коллекции зафиксированы в README, маршруты API wish-list и переноса определены в README. Общая база и специализированные модели записей, типы JSON и mapping колонок обоих документов согласованы в правилах данных.
- **Причина первоначального откладывания (история):** Первый прототип сознательно использует только локальные тестовые данные без внешних сервисов.

## 10. Проверка структуры и ожидаемых колонок Google Sheets

- **Этап:** 1. **Статус:** реализовано для GET/POST/DELETE обеих коллекций; автоматические тесты пройдены. **Требования:** [документ](data-rules.md).

- **Описание:** Проверка структуры и ожидаемых колонок обеих коллекций определена в правилах данных и переиспользуется при GET/POST/DELETE и переносе.
- **Причина первоначального откладывания (история):** Реальные документы пока не подключены; это задача этапа интеграции.

## 11. Защита от повторной записи при timeout/retry/idempotency

- **Этап:** 1. **Статус:** реализовано для обеих коллекций и переноса; ограничения междокументной операции согласованы. **Требования:** [документ](data-rules.md).

- **Описание:** Для POST/DELETE основной коллекции нет автоматических повторных записей, результат проверяется перечитыванием; при неопределённости нужно обновить коллекцию. Отсутствие строки после timeout POST не доказывает окончательный отказ записи. Запросы записи одного процесса выполняются последовательно. Это не полноценная идемпотентность и не транзакционная защита от внешней конкурентной записи. Перенос не повторяет создание вслепую: дубли требуют выбора и подтверждения завершения удаления. Строгая атомарность и persistent journal не реализуются в MVP.
- **Причина первоначального откладывания (история):** Текущий прототип не выполняет запись. Конкретный механизм нужно выбрать при реализации внешних изменений.

## 12. Ошибки внешних сервисов и восстановление после сбоев

- **Этап:** 1. **Статус:** реализовано для обеих коллекций и переноса; реальный acceptance wish-list предстоит. **Требования:** [документ](data-rules.md).

- **Описание:** Для основной коллекции реализованы безопасные ошибки GET/POST/DELETE и состояние «Результат операции не подтверждён»; успех требует проверки результата. Контролируемый реальный acceptance записи пройден. Для wish-list применяется тот же подход, для переноса добавлен явный частичный успех без автоматического отката и автоматическое перечитывание обоих источников с защитой от устаревшего GET.
- **Причина первоначального откладывания (история):** В текущем прототипе внешние сервисы отсутствуют. Обработка ошибки загрузки локального JSON уже относится к прототипу и не откладывается этим пунктом.

## 18. Публикация приложения на собственном VPS

- **Этап:** 2. **Статус:** требует спецификации. **Требования:** [документ](../README.md).

## 19. Публичный режим просмотра коллекции

- **Этап:** 2. **Статус:** требует спецификации. **Требования:** [документ](../README.md).

- **Описание:** Дать другим людям возможность открыть приложение по ссылке и посмотреть коллекцию владельца. Публичный посетитель работает только в режиме **read-only**: добавление, редактирование и удаление пластинок посторонним недоступны. Публичный интерфейс должен хорошо представлять коллекцию и сам проект, позволяя использовать приложение как демонстрационный pet project — показать на собеседовании или приложить ссылку к портфолио. В дальнейшем можно добавить публичную статистику, фильтры, поиск, карточки пластинок и другие функции, интересные посетителю. **Регистрация пользователей и ведение отдельных коллекций не входят в это направление развития.**
- **Причина первоначального откладывания (история):** Текущий прототип предназначен для локального просмотра тестовых данных; публичное представление реальной коллекции и разграничение доступа относятся к будущему этапу.

- **Граница:** На этапе 2 согласован только гостевой просмотр. Видимые гостю поля и авторизация владельца требуют согласования; статистика, публичный поиск, карточки и другие расширения не включены автоматически.

- **Описание:** Дать нескольким пользователям возможность независимо вести собственные коллекции. Проработать authentication, принадлежность и изоляцию данных пользователей, права доступа, изменения API и модели хранения, переход от существующей однопользовательской модели и другие необходимые архитектурные изменения.
- **Почему отложено:** Многопользовательский режим требует отдельного проектирования и проверки изоляции данных. Система authentication и архитектура multi-user пока не выбраны.
- **Граница:** Это отдельный будущий этап; однопользовательские границы этапов 1–3 и гостевой read-only режим этапа 2 сохраняются без изменений.
