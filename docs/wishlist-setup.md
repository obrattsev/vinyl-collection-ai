# Подготовка wish-list и пользовательский acceptance

Структура соответствует единственному mapping в [правилах данных](data-rules.md). Два отдельных документа сохраняются. Существующий документ «Vinyl Collection AI — Wishlist», вкладка `Wishlist`, уже содержит нужные заголовки; создавать ещё один документ не требуется. Серверный service account получил доступ «Редактор» по явному подтверждению владельца 2026-09-22. Реальное чтение обоих документов проверено; на момент проверки оба пусты. Строки в реальных документах этой реализацией не добавлялись и не удалялись.

## Точная структура

Первая строка — заголовки без дополнительных строк названия, объединённых ячеек и формул:

| Колонка | Заголовок | JSON |
| --- | --- | --- |
| A | ID | id |
| B | Исполнитель | artist |
| C | Альбом | album |
| D | Жанр | genre |
| E | Дополнительный жанр | additionalGenre |
| F | Лейбл | label |
| G | Год альбома | albumYear |
| H | Год пластинки | recordYear |
| I | Тип издания | editionType |
| J | Примечание | note |
| K | Ссылка на онлайн-магазин | storeUrl |

Все 11 заголовков обязательны, их порядок может отличаться. Обязательные значения строки: UUID, Исполнитель, Альбом, Год альбома. Необязательные ячейки пусты, не содержат буквальный текст `null` или `—`. Годы — четыре цифры. При добавлении через UI UUID назначает сервер. Обычный GET не мигрирует и не исправляет записи.

Для нового окружения: создать отдельный документ с этими заголовками; предоставить существующему серверному service account право «Редактор» только на этот документ; указать `WISHLIST_SPREADSHEET_ID` и `WISHLIST_SHEET_NAME=Wishlist` в локальном `.env`. Ключ остаётся вне Git и не передаётся браузеру. Перед созданием/изменением реальной таблицы и доступов сообщить владельцу точный состав действий. Оба незаполненных параметра дают явное «Wish-list не подключён», не локальный JSON.

## Одна acceptance-итерация

1. Открыть `/prototype/wishlist.html`, нажать «Показать весь wish-list» и зафиксировать исходное состояние обоих документов. Для пустого wish-list проверить отдельное сообщение.
2. Добавить первый и второй вымышленные примеры через форму: проверить обязательные поля, ошибочный URL, разные жанры, просмотр полного проекта, «Исправить» и «Отмена». До подтверждения записи не выполняются.
3. Найти первый пример по части исполнителя, затем по полному имени без выбора режима. Проверить дополнительный жанр, совместные критерии и пустой поиск. «Очистить» не выполняет поиск и не меняет результаты.
4. Повторить первый проект: подтверждённый дубль издания блокирует запись. Третий пример другого издания допустим. После переноса первого примера в коллекцию форма третьего должна показывать предупреждение о наличии альбома в коллекции.
5. Открыть удаление второго примера, отменить; проверить, что запись осталась. Снова открыть и подтвердить; проверить исчезновение только его UUID.
6. Перенести первый пример: оставить необязательную дату/магазин пустыми, указать цену `0`, просмотреть полный проект, подтвердить. Проверить появление записи с отдельным UUID в коллекции и исчезновение исходника из wish-list. Wish-list обновляется автоматически, без ручной синхронизации.
7. Частичные сбои и конфликт версии проверены автоматическими тестами с подменённым Google; не создавать их повреждением реальных таблиц. При реальном частичном успехе дождаться автоматического обновления, повторно выбрать перенос оставшегося исходника и явно выбрать уже существующую запись коллекции для завершения удаления. Потенциальное совпадение не доказывает, что это прошлый перенос.
8. Удалить только созданные acceptance-записи из обоих разделов с подтверждением и сверить исходный состав. Временные данные не оставлять без явного согласования. При пустом исходном состоянии после очистки оба API должны вернуть `[]`.

Автоматические тесты используют подменённый Google API; подготовленные примеры не служат runtime fallback. Реальный изменяющий acceptance должен быть отмечен отдельно после прохождения владельцем.
