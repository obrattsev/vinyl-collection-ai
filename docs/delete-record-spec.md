# Удаление записи коллекции и wish-list

Статус: сценарий согласован; интеграция основной коллекции реализована, контролируемый реальный acceptance удаления пройден. Интеграция wish-list реализована и покрыта автоматическими тестами; реальный acceptance пройден по подтверждению владельца. Этап: 1.
Связанные документы: [правила данных](data-rules.md), [backlog](backlog.md).

## Сценарий

Операция входит в локальный MVP обеих таблиц и выполняется через веб-интерфейс без AI.

1. Пользователь выбирает запись в основной коллекции или wish-list.
2. Приложение показывает подтверждение удаления выбранной записи.
3. Пользователь подтверждает удаление. До подтверждения данные не изменяются; при отмене запись сохраняется.
4. Приложение удаляет выбранную запись из соответствующего Google Sheets-документа.
5. Приложение проверяет результат удаления.
6. Только после успешной проверки сообщает об успешном удалении.

Посторонние записи не должны изменяться. Ошибка или неопределённый результат удаления не выдаются за успех. Undo не входит в текущий MVP; идея сохранена как будущее UX-улучшение в [backlog — Undo после удаления](backlog.md#undo-после-удаления).

Для основной коллекции используется `DELETE /api/collection/:id` через собственный API и слой доступа к данным. В обеих коллекциях запись идентифицируется по постоянному UUID из [правил данных](data-rules.md#постоянный-id-записей), не по номеру строки Sheets. Удаление не перенумеровывает оставшиеся записи; удалённый ID не переиспользуется. Успешный ответ — `200 OK` и фактически удалённый `CollectionRecord` в JSON. Если запись не найдена — `404`. Базовые ошибки и общий JSON-формат с полем `error` определены в [контракте API](../README.md#архитектура-доступа-к-данным-и-api). Для wish-list используется `DELETE /api/wishlist/:id`, успешный ответ содержит удалённый `WishlistRecord`; модель записи — `WishlistRecord` по общим правилам данных.

## Подтверждение и проверка основной коллекции

- Подтверждение показывает все пользовательские поля выбранной записи. DELETE передаёт UUID и `If-Match` с отпечатком показанного `CollectionRecord` по [контракту API](../README.md#подтверждение-и-ошибки-записи-основной-коллекции).
- Перед удалением данные перечитываются. Если запись изменилась после открытия подтверждения, удаление блокируется ответом `409 RECORD_CHANGED`; интерфейс показывает актуальную запись и требует подтвердить её заново. Если запись исчезла — `404 NOT_FOUND`.
- Слой доступа заново находит физическую строку по UUID непосредственно перед удалением. После операции приложение перечитывает коллекцию, проверяет отсутствие удаляемого UUID и сохранность остальных записей. Только после этого возвращается `200` с удалённой записью.
- При потере ответа на запись автоматического повторного удаления нет. Приложение проверяет результат чтением; если подтвердить его нельзя, возвращает `RESULT_UNCONFIRMED`. Пользователь видит «Результат операции не подтверждён» и должен обновить коллекцию перед дальнейшими изменениями. Повторный DELETE уже отсутствующего UUID возвращает `404`.
- Последовательное выполнение записей защищает запросы одного процесса приложения; внешние одновременные изменения Sheets не защищены транзакцией. Сохраняется ограничение однопользовательского MVP из общих правил данных.

## Удаление wish-list

Wish-list использует тот же порядок подтверждения, проверки версии, перечитывания результата и отсутствия автоматического повтора. Ревизия охватывает 11 полей `WISHLIST_FIELDS`. Ошибки источника и модели имеют префикс `WISHLIST_`. После неопределённого результата требуется обновление; старый GET не снимает блокировку. Завершение удаления при частичном переносе описано в [контракте переноса](add-wishlist-record-spec.md#перенос-wish-list--collection). Массовые операции, архивирование, история и Undo не добавляются.
