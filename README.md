# Vinyl Collection AI

Приложение для ведения домашней коллекции виниловых пластинок. Название проекта сохранено; AI появится на третьем этапе.

## Этапы

1. **Полноценный локальный MVP без AI.** Один владелец, веб-интерфейс с таблицами, формами и фильтрами. Просмотр и поиск в коллекции и wish-list, ручное добавление, редактирование и удаление, проверки дублей и форматов, подтверждение изменений и отмена. Хранилище — два отдельных реальных Google Sheets-документа. Локальный запуск требует интернета для Google Sheets.
2. **Доступ через интернет.** После реализации и тестирования первого MVP: публикация на собственном VPS, HTTPS, полный доступ владельца и публичный гостевой read-only просмотр разрешённых данных коллекции. Авторизацию и состав гостевых данных согласовать до реализации. Отдельные коллекции других пользователей не предусмотрены.
3. **AI-чат.** Дополнительный интерфейс к существующим операциям; формы и кнопки сохраняются. Естественный язык, фото, уточнение сведений в интернете и неоднозначных написаний — только на этом этапе. Провайдер, расходы и подробности реализации ещё не выбраны.

## Границы первого MVP

- Коллекция и wish-list доступны через отдельные разделы; добавление выполняется в явно выбранный раздел.
- Дополнительный жанр включён в модель этапа 1; он необязателен и при заполнении отличается от основного жанра по общим правилам данных. Поиск по жанру проверяет оба поля.
- Ручной поиск основной коллекции содержит только Исполнитель, Альбом, Год альбома и Жанр. Текстовые критерии сопоставляются автоматически: учитываются и точное совпадение нормализованного значения, и вхождение введённого текста. Все подходящие записи показываются без ранжирования и без скрытия частичных совпадений при наличии точных. Выбора режима в UI нет. Год альбома — только точное совпадение YYYY. Все заполненные критерии применяются совместно (И); пустой критерий отключает фильтр по полю. Единый критерий Жанр проверяет оба жанровых поля; отдельного критерия Дополнительный жанр нет.
- Кнопка «Очистить» в ручном поиске основной коллекции очищает четыре критерия, не выполняя поиск и не изменяя данные коллекции. Отдельной бизнес-операции «Отмена» для этого поиска нет.
- Поиск по остальным полям основной коллекции не входит в ручной интерфейс; модель данных сохраняется. Гибкий и расширенный поиск относится к AI-интерфейсу этапа 3. Поиск wish-list определяется его отдельной спецификацией.
- Изменения требуют предварительного показа проекта и подтверждения. Отмена отбрасывает несохранённый проект без автоматического продолжения.
- Потенциальный дубль блокирует добавление; подтверждение не отменяет эту проверку.
- Автоматически нормализуются только технические различия по общим правилам данных (регистр и лишние пробелы). Смысловая проверка названий, распознавание фото, AI и интеграции с музыкальными каталогами в первый этап не входят. Пользователь вводит сведения самостоятельно.
- Проверки дублей и консистентности встроены в операции; самостоятельная проверка всей коллекции не включена.

## Архитектура доступа к данным и API

Статус: реализованы GET, POST и DELETE основной коллекции и соответствующие сценарии UI. Добавление и удаление проверены автоматическими тестами с подменённым Google API и контролируемым acceptance в реальной таблице с разрешения владельца. API wish-list и редактирование не реализованы; весь этап 1 ещё не завершён.

`UI → собственный API приложения → слой доступа к данным → Google Sheets`

Browser/UI не обращается напрямую к Google Sheets API. UI работает со стандартной внутренней моделью Vinyl Collection AI и не знает ID Google Sheets-документа, названий листов, формата Google Sheets API или способа авторизации Google. Слой доступа к данным преобразует представление хранилища во внутреннюю модель и позволяет в будущем заменить Google Sheets без изменения бизнес-логики, минимизируя изменения UI. Коллекция и wish-list сохраняются в двух отдельных документах; маршруты API wish-list в этой итерации не определяются. Внутренняя модель — общая база `BaseRecord` и специализированные `CollectionRecord` и `WishlistRecord`; UUID обязателен в обеих моделях.

Для уже предусмотренных операций основной коллекции:

| Запрос | Назначение и согласованная часть контракта |
| --- | --- |
| `GET /api/collection` | `200 OK` + JSON-массив записей основной коллекции во внутренней модели приложения; для пустой коллекции — `[]`. |
| `POST /api/collection` | Создать запись; данные передаются JSON в body. `201 Created` + фактически созданная запись в JSON с UUID, присвоенным приложением. |
| `DELETE /api/collection/:id` | Удалить запись по постоянному UUID, не номеру строки Sheets. `200 OK` + фактически удалённая запись в JSON. |

API сохраняет проверки и подтверждения существующих операций; успех сообщается только после проверки результата. Правила технического UUID, миграции и целостности ID — в [модели данных](docs/data-rules.md#постоянный-id-записей).

Базовые коды ошибок:

- `400` — некорректный запрос/данные;
- `404` — запись не найдена;
- `409` — конфликт с бизнес-правилами;
- `500` — внутренняя ошибка.

Ошибки возвращаются единообразным JSON-объектом как минимум с полем `error`. В текущем GET статус `500` различается по значению `error`: `COLLECTION_DATA_INVALID` — нарушение структуры/целостности данных, `COLLECTION_SOURCE_UNAVAILABLE` — ошибка чтения Google Sheets или аутентификации Google, `INTERNAL_ERROR` — непредвиденная внутренняя ошибка. Внутренние исключения и конфигурация клиенту не передаются. GET не создаёт и не исправляет ID. Корректная таблица с заголовками и без записей возвращает `200 []`; ошибки не подменяются пустым массивом.

Окончательный механизм authentication остаётся открытым. До публичного deployment изменяющие операции `POST` и `DELETE` должны получить защиту; публиковать их незащищёнными нельзя. Для серверного чтения и записи Google используется service account с доступом «Редактор» только к документу основной коллекции и scope `spreadsheets`; локальный JSON-ключ хранится вне репозитория. Это не авторизация пользователя приложения. Имена, типы, обязательность и соответствие колонкам Sheets определены в [JSON mapping](docs/data-rules.md#внутренние-модели-и-google-sheets-mapping). Все ключи соответствующей модели присутствуют: пустые необязательные значения — `null`, неприменимые поля отсутствуют. Основная коллекция возвращается как `CollectionRecord`; формы успешных ответов и базовый формат ошибок определены выше. Собственный API не означает публикацию приложения в интернете; продуктовые этапы не меняются.

## Подтверждение и ошибки записи основной коллекции

POST принимает все 12 пользовательских полей без `id`; необязательные пустые значения — `null`. UUID назначает сервер. UI показывает полный проект, даёт исправить его или отменить, затем отправляет POST только по явному подтверждению. Сервер повторно проверяет форматы и дубли; успех возвращается после перечитывания созданной записи и сверки всех значений.

Форма ограничивает ввод даты шаблоном YYYY-MM-DD и цены неотрицательной суммой с максимум двумя знаками копеек. Оба необязательных жанра выбираются из одного закрытого справочника; сохранённые значения и поиск не изменяются. Ошибки показываются у конкретных полей; подробности — в [спецификации формы](docs/add-record-spec.md#ввод-и-обратная-связь-формы). После записи выполняется новое чтение; устаревшие ответы GET не перезаписывают список.

DELETE передаёт заголовок `If-Match` — SHA-256 подтверждённого `CollectionRecord` в двойных кавычках. Общая функция `recordRevision` вычисляет его по JSON-массиву значений всех 13 полей в порядке `COLLECTION_FIELDS`. Это проверка версии, не authentication. Если данные изменились, сервер возвращает `409 RECORD_CHANGED` и актуальную запись в `record`; UI показывает её и требует нового подтверждения. Исчезнувшая запись — `404 NOT_FOUND`. После удаления сервер проверяет отсутствие UUID и сохранность остальных записей; успешный ответ содержит удалённую запись.

Дополнительные ошибки записи: `400 INVALID_REQUEST` — неверный JSON, тип запроса или подтверждение; `400 INVALID_RECORD` — неверные поля проекта; `409 POTENTIAL_DUPLICATE` — потенциальные дубли в `records`; `500 RESULT_UNCONFIRMED` — результат записи не удалось подтвердить, поле `id` указывает проверяемый UUID. Внутренние исключения не выдаются. Повторной автоматической записи нет: после попытки сервер перечитывает данные. Даже потерянный ответ Google не мешает успеху, если результат подтверждён чтением. Если подтвердить нельзя, UI показывает «Результат операции не подтверждён» и требует обновить коллекцию перед дальнейшими изменениями. Отсутствие строки после timeout POST не доказывает, что запись не завершится позже.

Изменяющие запросы принимаются только для локального `Host` 127.0.0.1; чужой `Origin`/cross-site запрос отклоняется (`403 FORBIDDEN`). Это локальная защита от запросов сторонних страниц, не согласованная авторизация для публичного deployment. Не запускайте несколько серверов записи и не меняйте/не сортируйте таблицу вручную одновременно с операцией: Sheets не предоставляет транзакционную защиту между чтением UUID и удалением физической строки. Полная защита от внешней конкурентной записи остаётся вне текущего однопользовательского MVP.

## Локальный запуск

Требуются Node.js 24 LTS с npm, браузер и доступ к Google Sheets. Это срез просмотра, поиска, добавления и удаления основной коллекции этапа 1, а не завершённый MVP. Сервер и UI запускаются одним процессом; Python-сервер больше не используется.

1. Создайте локальный `.env` по `.env.example` в корне проекта. `.env` исключён из Git. Заполните `COLLECTION_SPREADSHEET_ID` (ID документа, не `gid`), `COLLECTION_SHEET_NAME` (точное имя вкладки), `GOOGLE_APPLICATION_CREDENTIALS` (абсолютный путь к JSON-ключу вне репозитория), `PORT` (по умолчанию 8000).
2. В Google Cloud включите Google Sheets API. Предоставьте service account доступ «Редактор» только к документу основной коллекции. Не добавляйте ключ в проект, браузерный код или Git. GET не изменяет данные; право записи используется после подтверждения добавления или удаления.
3. Из корня репозитория выполните:

```bash
npm ci
npm start
```

Откройте http://127.0.0.1:8000/prototype/. Сервер слушает только `127.0.0.1`, раздаёт явно разрешённые клиентские файлы и API основной коллекции. `.env`, серверные модули и другие служебные файлы через HTTP недоступны. Остановка — `Ctrl+C`.

При «Найти» и «Показать всю коллекцию» UI получает актуальный массив `CollectionRecord` через `/api/collection`, затем применяет существующую бизнес-логику поиска. `prototype/data/collection.json` пока сохранён как прежний пример, но не используется ни как источник, ни как fallback и не раздаётся сервером. Восемь отображаемых полей таблицы сохранены; добавлена колонка действий с кнопкой удаления. UUID остаётся в данных ответа.

## Подготовка таблицы и ручная проверка

Заголовки и форматы должны соответствовать [правилам данных](docs/data-rules.md). В подготовленном с нуля документе — четыре вымышленные тестовые записи с UUID. Миграция для них не требуется; GET никогда не выполняет миграцию и не изменяет таблицу. API wish-list в этот срез не входит.

- «Показать всю коллекцию» возвращает все четыре подготовленные записи независимо от критериев формы.
- Исполнитель `Орбита`, Альбом `Сигнал`, Год альбома `1990`, Жанр `Progressive Rock` возвращают два издания; жанр совпадает в дополнительном поле.
- При тех же критериях и годе `2020` совпадений нет. Неполный год показывает ошибку критериев.
- «Очистить» сбрасывает форму без нового запроса и без изменения показанных результатов. Поиск с пустыми критериями показывает всю коллекцию.
- Пустая корректная таблица отличается от отсутствия совпадений. Ошибка API показывает только «Ошибка загрузки данных. Не удалось загрузить коллекцию.». Эти состояния также проверяются автоматическими тестами без изменения реальной таблицы.

## Модули и тесты

- `server/index.mjs` — конфигурация и запуск; `server/app.mjs` — GET/POST/DELETE и ограниченная статическая раздача.
- `server/collection-service.mjs` — проверка проекта, дублей, подтверждённой версии и результата записи; последовательное выполнение изменений внутри одного процесса.
- `server/google-sheets-collection.mjs` — чтение, добавление и удаление Google Sheets, mapping и преобразование значений; единственная прямая runtime-зависимость — `google-auth-library`.
- `src/collection-record.mjs` проверяет полную модель, обязательные значения и уникальность UUID без исправлений. При ошибке вся загрузка отклоняется, повреждённые записи не отбрасываются молча.
- `src/collection-rules.mjs` сохраняет независимые от хранилища правила поиска и сравнения. Проверка потенциальных дублей не добавляет новую блокировку GET.

```bash
npm test
```

Тесты используют встроенный `node:test`, подменённый Google-клиент и локальный HTTP-сервер. Реальная таблица, credentials и сеть Google им не нужны. Проверка реального GET выполняется отдельно после настройки доступа. Реальные добавление и удаление тестовой записи выполняются только в согласованном acceptance. Недоступность источника не должна подменяться локальными данными.

## Acceptance добавления и удаления

1. Загрузите коллекцию и зафиксируйте её исходный состав. Не используйте существующую запись для пробного удаления.
2. «Добавить пластинку»: заполните явно тестовые Исполнитель, Альбом и Год альбома; проверьте `0` цены и пустые необязательные поля. Просмотрите полный проект; «Исправить» требует повторного просмотра, «Отмена» не записывает данные.
3. После согласования реальной записи подтвердите проект. Проверьте появление ровно одной строки с новым UUID, сохранность старых строк и поиск новой записи.
4. Попробуйте тот же проект: дубль должен блокироваться без записи. Отмена закрывает форму.
5. После разрешения на реальное удаление выберите только созданную тестовую запись: сначала отмените, затем откройте подтверждение заново и подтвердите. Проверьте отсутствие её UUID и неизменность исходных записей.
6. Изменение записи после открытия подтверждения, timeout и ошибки проверяются на подменённом источнике; не повреждайте реальную таблицу для этих проверок.

Контролируемый acceptance 2026-09-21 пройден через UI: добавление одной тестовой записи, поиск, блокировка дубля (409), отмена удаления и подтверждённое удаление. Цена 0 и null проверены через API. После удаления все четыре исходные записи (все 13 полей) полностью совпали с состоянием до проверки. Сценарии timeout и конфликта изменённой записи проверены на подменённом источнике, а не путём повреждения реальной таблицы.
