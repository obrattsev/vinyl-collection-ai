# Добавление в wish-list

Статус: реализовано для интерфейса без AI; автоматические тесты пройдены, реальный acceptance записи предстоит. Этап: 1.
Связанные документы: [правила данных](data-rules.md), [будущий AI](ai-stage.md), [backlog](backlog.md).

## Сценарий

1. Пользователь открывает добавление в явно выбранном разделе «wish-list». Целевой раздел виден в форме и при подтверждении; технические ID документа и названия листов Google Sheets UI не использует.
2. Вручную заполняет пользовательские обязательные и выбранные необязательные поля из правил данных, включая дополнительный жанр. Существующие написания предлагаются как подсказки, не применяются автоматически.
3. Приложение проверяет обязательность и форматы, нормализует значения только для сравнения. Проверить потенциальные дубли в wish-list и основной коллекции. При совпадении альбома в коллекции показать предупреждение и найденные записи; подтверждённый дубль издания блокирует добавление. Неизвестные признаки дают предупреждение с возможностью подтвердить проект по общим правилам данных. Действия формы имеют [общую раскладку](add-record-spec.md#общие-действия-интерфейса).
4. Показывает полный проект новой строки. Пользователь может исправить данные, отменить операцию или подтвердить проект. Исправленный проект проверяется и подтверждается заново.
5. После подтверждения повторно проверяет форматы и дубли по актуальным данным.
6. Приложение генерирует постоянный UUID по [общим правилам данных](data-rules.md#постоянный-id-записей); пользователь не задаёт ID при обычном добавлении. Добавляет ровно одну строку в конец целевого документа, не перезаписывая существующие строки.
7. Перечитывает добавленную строку и сравнивает с подтверждённым проектом. Сообщает успех только после проверки.

При интеграции UI использует `WishlistRecord` по общему mapping; запись выполняется через собственный API и слой доступа к данным. Пользовательские значения сверяются с подтверждённым проектом, назначенный ID — с записанным ID. `POST /api/wishlist` принимает все 10 пользовательских полей, возвращает `201` и полный проверенный `WishlistRecord`. Основной и дополнительный жанры в форме используют общий закрытый справочник; подсказки исполнителя, альбома и лейбла читаются из обоих документов. Ошибки показываются у полей; URL отображается текстом без исполнения содержимого.

## Критерии приёмки

- Все пользовательские общие поля и поля целевого документа доступны; обязательные поля заполнены, форматы соблюдены.
- Подтверждённый дубль не добавляется даже после подтверждения. Неизвестные признаки издания дают предупреждение с возможностью подтвердить добавление по [общим правилам](data-rules.md#потенциальные-дубли-при-добавлении).
- До подтверждения и после отмены запись не выполняется.
- Успешное добавление создаёт одну строку в конце, совпадающую с проектом; существующие данные обоих документов сохраняются.
- Ошибки и неопределённый результат записи не выдаются за успех; после попытки записи результат перечитывается и проверяется. Автоматического повторного добавления нет. При `RESULT_UNCONFIRMED` пользователь обновляет данные перед следующими изменениями. Отсутствие строки после timeout не доказывает окончательный отказ записи.

Фото, AI-команды и интернет-уточнение перенесены на этап 3. Перенос покупки является отдельной операцией, описанной ниже.

## Перенос wish-list → collection

Статус: согласовано владельцем 2026-09-22, реализовано. Сценарий не является обычным добавлением wish-list. Два отдельных Google Sheets-документа сохраняются; ограниченная неатомарность принята для MVP.

1. Пользователь выбирает «Добавить в коллекцию». UI показывает все поля исходника, позволяет ввести Дату покупки, Магазин покупки и Цену покупки, затем показывает полный проект коллекции для подтверждения. Общие поля исходника сохраняются; `storeUrl` отсутствует в коллекции. Поля покупки необязательны, цена 0 сохраняет значение «бесплатно».
2. Один `POST /api/wishlist/:id/transfer` передаёт `If-Match` исходного `WishlistRecord` и JSON из трёх ключей `purchaseDate`, `purchaseStore`, `purchasePrice` (пустые — `null`). API не принимает произвольную замену общих полей или клиентский UUID.
3. Сервер проверяет ревизию исходника, полную модель будущей коллекции и потенциальные дубли в коллекции. При конфликте до записи — `409 RECORD_CHANGED`, при дублях — `409 POTENTIAL_DUPLICATE` с найденными `records`; при отсутствии исходника — `404 NOT_FOUND`.
4. Сервер создаёт `CollectionRecord` с новым UUID и проверяет все её поля и сохранность остальных записей. При `RESULT_UNCONFIRMED` исходник не удаляется. Запись в Sheets автоматически не повторяется.
5. После подтверждённого создания сервер снова проверяет исходник и его ревизию, удаляет по UUID и проверяет отсутствие строки и сохранность остальных записей wish-list. Изменившийся исходник не удаляется.

Результаты:

- `200 { status: "complete", collectionRecord, wishlistId }` — создание и удаление проверены.
- `200 { status: "partial", collectionRecord, wishlistId, error: "TRANSFER_DELETE_INCOMPLETE", reason }` — запись коллекции подтверждена, удаление исходника не завершено или не подтверждено. `reason` содержит безопасный код, например `RECORD_CHANGED`, `NOT_FOUND`, `RESULT_UNCONFIRMED`, `WISHLIST_SOURCE_UNAVAILABLE`.
- `500 { error: "RESULT_UNCONFIRMED", id }` на этапе создания — его результат неизвестен; исходник не удаляется. Ошибки, возникшие до попытки создания, сохраняют обычный формат API.

При частичном успехе запись коллекции никогда автоматически не удаляется. UI сообщает отдельный результат и перечитывает оба документа. Технического блока и отдельной кнопки синхронизации нет: перечитывание выполняется автоматически после полного, частичного или неопределённого результата переноса. Если один источник недоступен, показывается ошибка, а блокировка дальнейших изменений не снимается до успешного обновления. Обычный повтор поиска или показа всего wish-list повторяет необходимые чтения обоих источников без отдельной операции синхронизации. Устаревшее чтение не может подменить новый результат или снять блокировку.

### Повторная попытка и завершение удаления

Без журнала приложение не может доказать, что найденная запись создана предыдущей попыткой. Повторный перенос сначала проверяет потенциальные совпадения: они блокируют новое создание даже при неполных признаках. Эта защита переноса намеренно строже обычного добавления с предупреждением: иначе после частичного успеха повтор мог бы создать ещё одну запись коллекции. Пользователь видит исходник и найденные записи коллекции, явно выбирает подходящую и подтверждает **только удаление wish-list**, без изменения коллекции. Никакого автоматического выбора совпадения нет.

Для этого тот же endpoint принимает `{ collectionId, collectionRevision }` вместо полей покупки. `If-Match` по-прежнему относится к исходнику. Сервер проверяет существование и обе ревизии, повторяет проверку потенциального совпадения и только затем удаляет wish-list. Неподходящая запись — `409 TRANSFER_TARGET_MISMATCH`. Изменение любой записи вызывает автоматическое обновление и требует нового подтверждения. Новая запись коллекции в этом режиме не создаётся; результат имеет ту же форму `complete`/`partial`.

### Ограничения

Одна общая очередь сериализует изменения обоих списков и перенос в одном процессе. Не запускать несколько серверов записи и не редактировать/сортировать Sheets вручную одновременно с операцией. Внешняя конкуренция, запоздалое применение Google после timeout и сбой между двумя документами не имеют строгой транзакционной защиты. При сомнении проверить фактические записи после автоматического перечитывания; при ошибке чтения повторить обычный поиск или показ всего wish-list. Persistent journal, инфраструктура идемпотентности и автоматический rollback не входят в этот MVP. Строгая атомарность — будущее улучшение при переходе на подходящее хранилище.
