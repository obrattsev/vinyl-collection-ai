# Stage 4D — ограничение удаления первоначального владельца

**Исследование без изменения механизма удаления. Реальные аккаунты не удалялись.** Основание — текущий локальный код и контракт Stage 4C; live production/личные данные не читались.

> Последующее решение владельца: защиту сохранить; локально кнопка protected delete скрыта, текст заменён на согласованное объяснение. Server rules не менялись. [Результат](stage-4d-statistics-local.md). Остальной документ фиксирует исходное исследование.

## Причина

Ограничение намеренное, прямо записано в `docs/stage-4c-local.md`, раздел «Смена пароля и удаление», и обеспечено сервером:

- `server/security/account-store.mjs`, `get`: `canDelete = user.id !== ownerId && !mirror && !session.legacy`.
- `remove`: первым отдельным условием запрещает `session.userId === ownerId` с `ACCOUNT_PROTECTED`, затем проверяет текущий пароль и подтверждение; внутри owner transaction отдельно отказывает любому пользователю с `mirror_state`.
- `prototype/auth-ui.mjs`: при `canDelete:false` отключает кнопку и показывает `#account-protected`.
- Сам текст «Удаление этого аккаунта пока недоступно» — статическая общая формулировка `prototype/auth.html`. Клиент не объясняет конкретную причину, потому что API передаёт только boolean. Слово «пока» не означает, что ограничение снимается таймером или после нового входа.

**Запрет распространяется не только на первоначального владельца.** Защищены настроенный `ownerId`, любой аккаунт с mirror, а также legacy-сессии без обычной подтверждённой авторизации. У первоначального владельца запрет сохраняется и после активации нового входа/выключения legacy bridge: это самостоятельная защита по owner UUID.

## Обычные пользователи

Обычный зарегистрированный пользователь без mirror может удалить собственный аккаунт после проверки действующей сессии, Origin/CSRF, текущего пароля и явного подтверждения. Чужой user ID клиент не выбирает: операция привязана к session.userId. Ограничения частоты и повторная проверка session/auth version под блокировкой сохранены.

В одной транзакции создаётся durable очередь очистки обложек, удаляются Collection/Wish-list (включая favorite), metadata Covers, auth flows, User; credentials и sessions удаляются каскадно. Файлы обложек очищаются после commit, ошибка диска оставляет очередь для retry. Логин остаётся зарезервированным. Записи Bug Reports по Stage 4D независимы от FK пользователя и не удаляются вместе с аккаунтом. Старые резервные копии не переписываются: риск возврата данных из старого backup и политика restore описаны в принятом контракте 4C; не обещать физическое уничтожение всех backup.

Проверка: существующий PostgreSQL integration suite 100/100, включая settings `canDelete:true` обычного пользователя и synthetic hard-delete с проверкой изоляции, очереди файлов, mirror/login reservation и отказа защищённому владельцу. Ни одного реального аккаунта эти тесты не затрагивают.

## Что будет при удалении владельца сейчас

Через штатный API операция отклоняется до удаления: данные, обложки и Google Sheets mirror не меняются.

Просто убрать кнопку/первый guard недостаточно и небезопасно:

1. Внутренний guard mirror продолжит запрещать операцию; FK `mirror_state.user_id → users.id ON DELETE RESTRICT` тоже не допускает простого DELETE User.
2. `server/index.mjs` проверяет согласованность mirror-конфига и строки mirror_state. Несогласованное ручное удаление состояния может остановить запуск приложения с `Mirror configuration/state mismatch`.
3. Mirror worker привязан к owner UUID и пишет в существующие Google Sheets. Штатная очистка аккаунта не очищает и не удаляет внешние таблицы. Без отдельной процедуры там останутся прежние данные или worker перейдёт в ошибку; синхронизация пустого списка после DELETE не гарантирована.
4. Снятие ограничений потребует согласованного изменения связей/конфигурации и проверок restore/deletion safety, затем обычной атомарной очистки записей и durable cleanup Covers. Прямое SQL-удаление обходит эти гарантии и не является решением.

## Предлагаемое решение

Сейчас оставить защиту. После отдельного согласования можно улучшить только объяснение в UI: API отдаёт безопасный reason-код, например `INITIAL_OWNER`/`MIRROR_ACCOUNT`/`ACTIVATION_REQUIRED`, интерфейс сообщает: «Удаление аккаунта владельца с настроенным зеркалом недоступно через личный кабинет». Это предложение, код не менялся.

Если самостоятельное удаление первоначального владельца действительно требуется, оформить отдельную задачу offboarding: решить судьбу сайта/владельца и внешних Sheets, остановить/отвязать его mirror, согласованно обновить owner/mirror configuration и DB state, проверить последующий запуск/backup/restore, затем разрешить стандартное защищённое удаление и cleanup Covers. Очистка внешних Sheets и реального аккаунта потребуют отдельного явного разрешения. Без этой подготовки ограничение снимать не следует.
