# Общие правила данных

Статус: действующие правила завершённого локального MVP этапа 1; условная legacy-миграция и будущие возможности отмечены отдельно. Связанные документы: [README](../README.md), [backlog](backlog.md).

## Хранение и поля

На этапе 1 используются два отдельных реальных документа Google Sheets: коллекция и wish-list. Один владелец. В коллекции одна строка — один приобретённый физический экземпляр издания целиком; в wish-list — одна желаемая пластинка или конкретное желаемое издание. Многодисковые комплекты и box set не разбиваются на диски.

Общие поля: техническое поле ID (обязательно), Исполнитель (обязательно), Альбом (обязательно), Жанр, Дополнительный жанр, Лейбл, Год альбома (обязательно), Год пластинки, Тип издания, Примечание.

Только коллекция: Дата покупки, Магазин покупки, Цена покупки. Только wish-list: Ссылка на онлайн-магазин.

Состав модели данных не ограничивается критериями ручного поиска. На этапе 1 [ручной поиск основной коллекции](search-records-spec.md) использует только Исполнитель, Альбом, Год альбома и единый критерий Жанр, проверяющий оба жанровых поля. Остальные поля сохраняются в модели; отдельного критерия Дополнительный жанр в этом интерфейсе нет.

Для box set: Альбом — официальное название комплекта; Исполнитель — основной исполнитель либо Various Artists при отсутствии единственного основного исполнителя; Год альбома — первый выпуск комплекта как самостоятельного релиза.

## Постоянный ID записей

- Каждая запись основной коллекции и wish-list получает постоянный уникальный UUID, генерируемый приложением при создании.
- UUID хранится отдельной колонкой `ID` Google Sheets. Это обязательное техническое поле обеих моделей; пользователь не задаёт его при обычном добавлении.
- ID не зависит от номера строки и не изменяется при сортировке, вставке или перемещении строк.
- После удаления ID других записей сохраняются; удалённые ID не переиспользуются.
- ID входит в JSON обеих моделей: UI получает его через API для операций над конкретной записью, но не обязан отображать в обычной таблице. `POST /api/collection` возвращает фактически созданную запись с присвоенным ID.
- Правила потенциальных дублей не меняются.
- Полноценная защита от конкурентных записей посредством транзакций/блокировок не входит в текущий однопользовательский MVP.

## Миграция и целостность ID

Текущие рабочие таблицы основной коллекции и wish-list уже используют UUID и не требуют миграции. Только при появлении legacy-записей без ID предусмотрена условная одноразовая миграция вне этапов: каждой такой строке присваивается UUID. Требование применимо к обоим Google Sheets-документам; оно не является незавершённой частью MVP или разрешением изменять реальные таблицы.

Обычный `GET` не создаёт и не исправляет ID. Отсутствующий, некорректный или повторяющийся ID считается нарушением целостности данных и приводит к явной ошибке в общем JSON-формате API с полем `error`, а не к автоматическому исправлению. Эти правила действуют для обоих документов. Условная legacy-миграция не реализована; для текущих данных не требуется.

## Внутренние модели и Google Sheets mapping

Статус: согласовано для API; чтение, mapping и API обеих коллекций реализованы. Условная legacy-миграция находится вне завершённого этапа 1. Используется общая базовая модель `BaseRecord` и специализированные `CollectionRecord` и `WishlistRecord`. Это логические схемы данных/API, а не требование реализовать классы или наследование. Слой доступа к данным преобразует колонки двух отдельных Google Sheets-документов в соответствующую модель.

Общие десять полей `BaseRecord` присутствуют в обеих моделях:

| Колонка Google Sheets | Поле JSON | Тип значения JSON | Обязательное значение |
| --- | --- | --- | --- |
| ID | `id` | string, UUID | Да |
| Исполнитель | `artist` | string | Да |
| Альбом | `album` | string | Да |
| Жанр | `genre` | string или null | Нет |
| Дополнительный жанр | `additionalGenre` | string или null | Нет |
| Лейбл | `label` | string или null | Нет |
| Год альбома | `albumYear` | string, YYYY | Да |
| Год пластинки | `recordYear` | string, YYYY, или null | Нет |
| Тип издания | `editionType` | string или null | Нет |
| Примечание | `note` | string или null | Нет |

`CollectionRecord` содержит все поля `BaseRecord` и три поля только основной коллекции (всего 13 ключей):

| Колонка Google Sheets | Поле JSON | Тип значения JSON | Обязательное значение |
| --- | --- | --- | --- |
| Дата покупки | `purchaseDate` | string, YYYY-MM-DD, или null | Нет |
| Магазин покупки | `purchaseStore` | string или null | Нет |
| Цена покупки | `purchasePrice` | number, рубли, или null | Нет |

`WishlistRecord` содержит все поля `BaseRecord` и одно поле только wish-list (всего 11 ключей):

| Колонка Google Sheets | Поле JSON | Тип значения JSON | Обязательное значение |
| --- | --- | --- | --- |
| Ссылка на онлайн-магазин | `storeUrl` | string, URL, или null | Нет |

JSON записи имеет стабильный набор всех ключей своей модели. Применимое необязательное поле без значения передаётся как `null`, а не пропускается и не заменяется пустой строкой. Пустые необязательные ячейки Sheets преобразуются в `null`. Неприменимые поля отсутствуют: у `CollectionRecord` нет `storeUrl`, у `WishlistRecord` нет `purchaseDate`, `purchaseStore`, `purchasePrice`.

Строковые значения передаются JSON-строками; годы также передаются строками, а цена — JSON number. Значения типа издания и остальные ограничения сохраняют форматы из следующего раздела. Цена `0` означает бесплатное получение, `null` — неизвестную цену. Отсутствие любого обязательного значения — нарушение целостности данных с явной ошибкой, а не допустимый `null`. Чтение не исправляет такие данные автоматически.

Схемы описывают полные записи, получаемые через API. При обычном добавлении пользователь не задаёт `id`: приложение присваивает UUID, а `POST /api/collection` возвращает полный `CollectionRecord` уже с ID. Маршруты API обеих моделей приведены в README.

## Структура Google Sheets при чтении обеих коллекций

- Заголовки находятся в первой строке и точно соответствуют mapping. Все ожидаемые колонки обязательны (13 в коллекции, 11 в wish-list), даже если значения необязательны; порядок произвольный.
- Отсутствующий или повторяющийся ожидаемый заголовок — ошибка. Дополнительные неизвестные колонки игнорируются при mapping.
- Полностью пустые строки игнорируются. Частично заполненная строка, в том числе с данными только в неизвестной колонке, проходит полную проверку записи. Пробельные ячейки считаются пустыми.
- Корректные заголовки без записей означают пустую коллекцию. Отсутствие самих заголовков — ошибка структуры.
- Слой доступа к данным читает неформатированные значения: числовые годы преобразуются в строки YYYY, числовые даты Sheets без времени — в YYYY-MM-DD. Текстовые даты принимаются только в согласованном формате; локализованные строки не угадываются. Цена должна быть числом либо пустой ячейкой.
- Чтение проверяет весь массив: при нарушении структуры, форматов, обязательности или уникальности UUID возвращается явная ошибка, без частичного результата и без исправления таблицы. Сравнение UUID для проверки уникальности не учитывает регистр; сохранённые значения не переписываются.

Подготовленные с нуля тестовые записи уже имеют UUID; одноразовая миграция для них не требуется. Миграция нужна только при появлении legacy-записей без ID и выполняется отдельно от обычного чтения.

## Форматы

- Годы: YYYY.
- Тип издания: Оригинал, Переиздание либо пусто (неизвестно).
- Оригинал — физическое издание первоначального выпуска, не обозначенное reissue/repress/remaster. Переиздание — последующий выпуск, включая reissue/repress/remaster. Совпадение годов не определяет тип автоматически; при неизвестном типе поле пустое.
- Дата покупки: полная календарная дата YYYY-MM-DD либо пусто. Неполная дата не хранится.
- Цена: конечное неотрицательное число в рублях. Пусто — неизвестно, 0 — бесплатно. Отдельного поля валюты нет. Форма добавления ограничивает ввод двумя знаками копеек по [спецификации](add-record-spec.md#ввод-и-обратная-связь-формы).
- Ссылка на магазин: корректный URL либо пусто.
- Дополнительный жанр необязателен; заполненное значение отличается от основного жанра после нормализации. Поиск по жанру проверяет оба поля (достаточно совпадения одного).

В ручных формах добавления обеих коллекций оба жанровых поля, а в поиске критерий Жанр используют единый закрытый [справочник](../src/genres.mjs). Это ограничение выбора в форме: существующие сохранённые жанры не переписываются и остаются доступными для чтения и поиска. Обязательность жанров, строковая модель данных и требования будущего AI-интерфейса этим изменением не меняются.

## Сравнение и консистентность

При сравнении игнорировать регистр и крайние пробелы, последовательности пробелов считать одним. Не изменять пунктуацию, дефисы, апострофы, слова или транслитерацию. Нормализация выполняется до любого сравнения; сохранённые значения автоматически не исправляются.

Предлагать существующие значения исполнителей, альбомов и лейблов; применение подсказки выбирает пользователь. Для коллекции учитывать коллекцию, для wish-list — оба документа. На этапе 1 автоматически нормализуются только технические различия, перечисленные выше. Смысловое исправление опечаток, сопоставление альтернативных написаний и другие AI-подобные проверки, включая проверку фактического существования релиза, не выполняются. Разные написания могут скрывать дубли — это явное ограничение; пользователь отвечает за введённые сведения. Семантические проверки перенесены в [этап 4](ai-stage.md).

## Потенциальные дубли при добавлении

Сначала сравнить Исполнитель + Альбом. При совпадении сравнить максимально доступные Лейбл + Год пластинки + Тип издания. Различие признака, заполненного в обеих записях, означает разные издания. Если различие не установлено, это потенциальный дубль: показать предупреждение и найденные записи. Неизвестное значение не доказывает совпадение: при неполных признаках пользователь может подтвердить добавление. Блокируется подтверждённый дубль — совпадающий альбом с заполненными и равными в обеих записях всеми тремя признаками издания (Лейбл, Год пластинки, Тип издания). Одного подтверждения недостаточно для обхода этой блокировки. Правило симметрично относительно существующей и новой записи; полностью неизвестное издание также даёт предупреждение, а не блокировку.

Для коллекции проверять существующие записи коллекции. Для wish-list проверять wish-list и коллекцию: совпадение альбома в коллекции требует предупреждения, а подтверждённое совпадение издания блокирует добавление. Другой выпуск того же альбома допустим. Например, Pink Floyd / More с неизвестными признаками не блокирует добавление 1986 / Переиздание: показывается предупреждение. Для переноса применяется отдельная защита повторной попытки: возможное совпадение требует выбора существующей записи и подтверждения завершения удаления, как описано в [контракте переноса](add-wishlist-record-spec.md#повторная-попытка-и-завершение-удаления).

## Подтверждение и отмена

Перед записью показать полный проект строки; исправления требуют просмотра и подтверждения обновлённого проекта. Перед редактированием и удалением также необходимо подтверждение. Редактирование не реализовано и относится к будущему этапу 3; его подробности требуют согласования; удаление выполняется по [согласованному сценарию](delete-record-spec.md), с сообщением об успехе только после проверки результата. Кнопка «Отмена» отбрасывает текущий неподтверждённый проект без записи и автоматического продолжения позже.

Для ручного поиска обеих коллекций вместо отдельной операции «Отмена» используется очистка формы по [спецификации поиска](search-records-spec.md): очищаются четыре критерия без нового поиска и изменения данных. Правила отмены остальных операций сохраняются.

## Состояние интеграции и ограничения

Для обеих моделей UUID, его хранение, условная legacy-миграция, правила целостности и JSON mapping определены выше. Проверка колонок при чтении обеих коллекций определена выше. Для основной коллекции поведение при изменении записи после подтверждения и неопределённом результате согласовано в [добавлении](add-record-spec.md) и [удалении](delete-record-spec.md): без автоматических повторных записей, с перечитыванием результата, новым подтверждением изменённой записи и обязательным обновлением коллекции при неопределённости. Приложение не сообщает успех без проверки результата. Для wish-list применяются те же правила конфликта версии и неопределённого результата. Контракт междокументного переноса с частичным успехом закреплён в [сценарии](add-wishlist-record-spec.md#перенос-wish-list--collection).

При переносе новая `CollectionRecord` получает отдельный UUID. Общие пользовательские поля сохраняются; `storeUrl` не превращается в неприменимое поле коллекции. Пользователь дополняет три поля покупки; все они по-прежнему необязательны. Перед удалением исходника проверяется ревизия всех 11 полей wish-list. Неподтверждённая операция не исправляет и не восстанавливает данные автоматически.
